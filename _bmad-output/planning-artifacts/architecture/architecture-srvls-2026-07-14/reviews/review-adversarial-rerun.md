# Adversarial Re-review — Architecture Spine

## Verdict

**REJECT — substantially improved, but the remaining ambiguities can still produce incompatible implementations or unsafe action targeting.** Identity, fixed export ordering, terminal ownership, privilege scope, and generation tagging now have explicit owners. The paths below are not yet closed.

## Remaining Findings

- **PM2 identity is still not immutable.** AD-13 calls PM2 numeric process ID plus `PM2_HOME` a native identity, but a PM2 ID can be removed and later assigned to another process. Re-resolving the same numeric ID immediately before mutation therefore does not prove it is the same observed resource. Include a process birth discriminator from `pm2_env` (for example creation timestamp plus execution path/name fingerprint) in the observed locator and require the executor to compare it before acting; the command may still use numeric ID after that check.

- **Provider-native grouping keys remain undefined.** AD-4 assigns provider-native evidence the top tier without defining which metadata fields form that evidence for Docker Compose, systemd, PM2, or cron. One implementation can use Compose project name while another uses working directory; one can derive systemd group evidence from unit slices while another declines to group systemd natively. Both obey the tier model and produce different default stacks. Specify the accepted native evidence fields, precedence, and canonical key for each provider.

- **“Exact normalized source” has no normalization contract.** The name-normalization pipeline is now concrete, but source normalization still permits lexical cleanup, basename extraction, absolute-path cleanup, symlink canonicalization, or ancestor-project discovery. Those choices change cross-provider groups and can depend on host filesystem state. Define per-provider source extraction and a purely lexical normalization algorithm, including trailing slashes, `.`/`..`, symlinks, missing paths, case, and whether a full path or basename is the evidence key.

- **Equal-tier conflict resolution still omits candidate-consumption semantics.** Member count, evidence specificity, and lexical key order resolve which candidate wins, but “specificity” is undefined and the rule does not say whether losing candidates are discarded whole, retried with unclaimed members, or split. Overlapping candidates can therefore yield different memberships while satisfying all tie-breakers. Define specificity as an ordered value and specify the complete greedy/graph algorithm, including candidate ordering and what happens to residual members.

- **Optional unavailability is not represented in the outcome algebra.** AD-5 says strict mode does not fail an optional missing tool, while `CollectorReport.outcome` has only `Unavailable` and no required/optional dimension or reason attached to the outcome. One implementation can treat all `Unavailable` as non-failing; another can inspect diagnostics to distinguish missing PM2 from an unavailable Docker daemon. Add an explicit availability policy/reason to the report and a total outcome-to-strict-exit mapping.

- **Partial outcome derivation is still caller-defined.** A systemd collector performs several operations and may obtain services while unit files or timers fail. AD-5 names `Partial` but does not say which combinations produce `Partial`, `Denied`, `TimedOut`, or `Failed`, nor whether one dominant outcome hides subsidiary faults. Independent adapters can classify the same captured fixture differently. Define a shared reduction table from process-result categories and sub-operation requiredness to collector outcome.

- **Canonical ordering contradicts exact brownfield compatibility for cron.** AD-9 sorts each bucket by legacy type, name, and `EntryId`, but the Python implementation emits cron entries in source/physical-line order. Both cannot simultaneously be the authoritative behavior if the baseline corpus includes multiple unsorted cron names. Decide whether stable sorted order is an intentional compatibility-ledger change or preserve source/line order; the present text directs implementers to satisfy incompatible contracts.

- **The compatibility corpus is still not singular or reproducible.** “Capture the Python baseline before replacement” allows separate implementers to capture different live cron contents, timestamps, load averages, tool versions, denial states, and ordering. Scrubbing can also change values relevant to escaping and identity. Name the committed fixture/golden paths and capture script, define normalization placeholders for volatile fields, and make that checked-in corpus—not a fresh host capture—the authority.

- **Action verification has no provider/verb success predicates.** AD-6 requires targeted-refresh verification but does not define what observation proves `start`, `stop`, `restart`, or `disable/delete`. A systemd `disable` can be verified by unit-file state while the service remains active; a restart can return to the same normalized state without proving a restart occurred; PM2 delete means absence. Define a verification predicate and timeout result for every provider/verb pair, including how absence, a replaced identity, and unavailable collectors map to `verified`, `unverified`, `stale`, or `failed`.

- **Targeted action refresh and normal refresh generations can race.** AD-10 permits only the latest requested generation to replace the displayed snapshot, but AD-6 requires a targeted refresh to verify an action. If a user/global refresh gets a newer generation first, one implementation can discard the action verification as stale while another can complete verification off-model and later merge its result. Define a separate operation correlation ID or generation lane for action verification and state whether its report may update the global snapshot.

- **Retained stale snapshots have no mutation policy.** AD-5 permits the TUI to retain a visibly stale last-good snapshot and AD-6 revalidates identity before mutation. One implementation can allow actions from stale rows after revalidation; another can disable all actions until current collection succeeds. Both comply, but the user-facing safety model diverges. Explicitly permit or forbid mutations initiated from stale snapshots and define the age/generation information included in confirmation.

- **Terminal restoration on process interrupt is not guaranteed by RAII alone.** Rust destructors do not run under the default terminating `SIGINT` disposition, and panic restoration depends on unwinding rather than `panic=abort`. AD-14 requires restoration on interrupt and unwind but names no signal interception/event path or panic strategy. Require `panic=unwind`, define how SIGINT/SIGTERM are converted into shutdown events, and state which signals are best-effort exceptions; otherwise two implementations can both claim RAII compliance while one leaves raw mode behind on Ctrl-C.

- **Privilege policy deliberately conflicts with the legacy action contract without recording the exception.** The Python CLI uses interactive `sudo systemctl` for system mutations, whereas AD-15 mandates `sudo -n`. This changes behavior, exit codes, and stderr for users without cached/passwordless authorization, while AD-9 says to preserve action exit behavior unless a compatibility-ledger entry exists. Add the explicit ledger decision and golden expectations for denial, or retain interactive behavior outside the TUI with a separately designed safe path.

- **The shared process-result algebra is referenced but not specified.** AD-15 enumerates categories, yet AD-3/AD-10 do not define a concrete result type or whether nonzero, signal, invalid UTF-8, and truncation carry captured stdout/stderr and may still be parsed. A runner returning `Ok(ProcessOutput { status: 1 })` and one returning `Err(Nonzero)` both satisfy the text but drive different diagnostics and partial outcomes. Specify the total result schema, truncation markers, lossy-decoding policy, and ownership of exit-status interpretation.

- **Operational compatibility depends on an unnamed glibc baseline.** AD-12 binds the binary to “the big-chungus glibc baseline” without recording the version or a reproducible build target. Builders can produce binaries with different minimum GLIBC symbol requirements and both claim compliance. Record the actual minimum glibc version, build environment/container, and verification command; otherwise the release and rollback contract is not testable.

- **Install and rollback behavior is not fully closed around the existing symlink.** The current installation points `~/.local/bin/srvls` at the repository script, while AD-12 introduces versioned binary directories and an atomic repoint. It does not define migration backup, rollback command, validation before repoint, or handling when the existing path is a regular file or foreign symlink. Specify the installer’s preconditions, ownership check, atomic-link algorithm, post-install smoke test, rollback procedure, and failure cleanup.
