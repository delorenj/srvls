# Adversarial Review — Architecture Spine

## Verdict

**REJECT — not yet deterministic enough to serve as a build substrate for independent coding agents.** The direction is sound, but the architecture decisions leave several shared contracts underspecified. In each finding below, two units can obey every stated AD and still produce incompatible behavior.

## Findings

- **Collector identity versus action lookup can disagree.** A Docker collector can derive `EntryId` from the full container ID while an action adapter derives it from the container name; both satisfy “provider-native identity” and AD-2/AD-3. The TUI can display an entry that the executor cannot resolve after selection, or act on a renamed/recreated container. Define the canonical native identity per provider, whether identity is snapshot-local or stable across recreation, and require action/inspection requests to carry that canonical locator rather than reconstruct it from display fields.

- **Cron entries have no defined unique identity.** One collector can key a cron entry by `(source, command)` while another can use `(source, line number, schedule, command)`; both are deterministic and provider-native under the current convention. Duplicate commands, schedule changes, comments, and line reordering then change deduplication and selection behavior. Specify a canonical cron locator and collision policy, including duplicate identical lines.

- **Entry ordering is unowned.** Collectors may append results in provider order while the collection use case may preserve worker-completion order; both comply with bounded concurrency and immutable snapshot ownership. JSON arrays, table rows, golden files, default selection, and stack member order can vary run to run. Assign canonical ordering to the snapshot or each presenter, with exact sort keys and tie-breakers based on stable identity.

- **Collector diagnostics can be modeled incompatibly.** AD-2 says `Entry` includes diagnostics while AD-5 says `InventorySnapshot` owns diagnostics. A collector can attach parse warnings to entries; another can emit only snapshot-level diagnostics; both comply. Presenters and `--strict` can therefore disagree about the same fault. Define diagnostic ownership, identity, scope (`collector`, `entry`, or `operation`), deduplication, and whether entry-level warnings count as collector errors for strict mode.

- **Partial success has no normative collector outcome.** A systemd collector can return entries plus `Failed` because timer enumeration failed, while another can return `Success` with a warning because service enumeration succeeded. Both make the failure visible and satisfy AD-5. `--strict`, TUI subsystem status, and telemetry then diverge. Define a result algebra that explicitly supports partial data and a normative severity-to-exit-status mapping.

- **Deadline ownership can create contradictory snapshots.** The collection orchestrator may abandon a timed-out worker and report `TimedOut`, while the worker may finish and send entries moments later; a receiver implementation can accept or discard those late entries while still using result abandonment as described by AD-10. Define the snapshot cut, channel protocol, generation ID, and rule that late results from an expired generation are discarded atomically.

- **Snapshot immutability does not define refresh replacement semantics.** A TUI model can replace the old snapshot wholesale after refresh, while another can retain old entries for failed collectors and overlay diagnostics; both treat each returned snapshot as immutable and reveal errors. One makes a subsystem disappear and the other displays stale resources as current. Define whether stale carry-forward is forbidden or represented explicitly with `observed_at`, collector generation, and stale state.

- **Grouping evidence precedence is not an executable contract.** One resolver can treat provider-native evidence as an absolute tier; another can combine multiple lower-tier scores so source plus semantic evidence beats provider-native evidence. Both choose the “strongest” scored non-conflicting evidence. Specify score ranges, tier precedence, aggregation rules, minimum thresholds, tie-breakers, and whether stronger evidence may ever be outweighed by accumulated weaker evidence.

- **“Non-conflicting” grouping is undefined.** Given Docker Compose group A, shared source group B, and overlapping name group C, one resolver can greedily assign entries in score order; another can maximize total score over the candidate graph. Both are deterministic and select strong non-conflicting evidence, but yield different stacks. Specify the conflict model, optimization/greedy algorithm, stable iteration order, and whether groups may merge transitively.

- **Name normalization is too open to independently implement.** One strategy can tokenize `foo-api-01`, `foo_api_02`, and `foo-api.service` as the same two-token prefix; another can preserve punctuation and treat `service` as a provider suffix only for systemd. Both satisfy the semantic-group rule. Provide a normative normalization pipeline: case folding, Unicode handling, separators, instance-number syntax, provider suffix list, generic-token list, minimum member count, and exact prefix extraction.

- **Source/location normalization is similarly ambiguous.** A Docker working directory `/srv/acme/prod` and PM2 cwd `/srv/acme/prod/app` can group by exact normalized path, basename, ancestor project root, or canonicalized path; all fit “normalized source/location.” Symlinks and nonexistent paths amplify divergence. Define the canonical source key per provider and whether filesystem canonicalization is allowed, required, or prohibited.

- **Stack labels and keys lack a canonical derivation.** The conventions list preferred labels but do not define stable group keys when evidence changes or multiple candidates share a label. One implementation can key by chosen evidence value; another can hash member IDs. Both separate key and label, yet TUI expansion/selection state can jump between refreshes. Define `StackGroupId`, label collision handling, and stability expectations across refreshes and membership changes.

- **Action capabilities can disagree with action execution.** A collector may infer capabilities from provider type (`docker` supports start/stop/restart/disable), while an executor may discover at execution time that the caller lacks permission or that a specific unit is static/masked. Both validate capabilities and use typed commands. The UI can enable an operation that is guaranteed to fail, or suppress one that would work. Separate intrinsic support from observed authorization/availability, define who owns each, and specify revalidation immediately before mutation.

- **`disable` and `delete` are conflated in the domain command.** One implementation can expose a single `Disable` command whose PM2 adapter maps to delete; another can define separate `Disable` and `Delete` variants and advertise only the applicable capability. Both preserve legacy mappings and satisfy typed-command execution. Confirmation language, audit events, and CLI parsing can differ on a destructive operation. Make the public verb, domain intent, provider-native operation, destructiveness classification, and confirmation copy explicit.

- **Mutation completion semantics are missing.** One executor can return success when `CommandRunner` exits zero; another can refresh and require the target state to be observed before success. Both execute through `ActionExecutor` after validation. The TUI may show “restarted” while the old snapshot remains selected, or block until a collector timeout. Define the mutation result contract, post-action refresh behavior, verification timeout, and how “command accepted but state unverified” is represented.

- **CLI and TUI can apply different confirmation policies while both comply.** AD-6 says destructive TUI actions require confirmation and explicit CLI verbs retain current behavior, but does not classify stop/restart/systemd-disable/Docker-stop/PM2-delete or define multi-entry stack actions. One TUI can confirm only PM2 deletion; another can confirm all `disable` actions. Define the destructive-action matrix and explicitly forbid stack-wide mutations in v1 or specify atomicity/partial-failure behavior.

- **Legacy JSON compatibility is not exact enough.** A presenter can map normalized status back to canonical strings, while another can preserve the raw provider status captured in metadata; both emit six `EntryV1` fields. Consumers matching `running(healthy)`, `active/running`, or `restarts:3` will see different values. Define the exact mapping for every provider and field, escaping/null/empty-string rules, array order, pretty-printing/newline behavior, and whether unknown raw values pass through.

- **Prometheus compatibility can diverge despite retaining metric families.** One presenter can aggregate using normalized status, another can reproduce the legacy string split (`/` then `(`), and both emit the current families. Problem detection, label values, quote/backslash escaping, ordering, and load-average failure behavior remain unspecified. Bind the Prometheus presenter to an exact compatibility algorithm and golden contract, not only family names.

- **Markdown and table compatibility are asserted but not specified.** One presenter can group Markdown by provider-neutral `EntryKind`; another can group by legacy `type` strings. One table can show inferred stacks by default while AD-9 says current text table is preserved. Both can plausibly satisfy “default presentation groups” and “legacy table behavior.” Explicitly state whether grouping applies only to TUI or also the bare non-TTY table, and normatively define legacy headings, widths, truncation, sort order, counts, timestamps, and Markdown escaping.

- **Terminal mode detection is underspecified.** One composition root can require both stdin and stdout to be TTYs; another can use stdout only and still interpret “when stdin/stdout are terminals” colloquially. Redirected stdin with an interactive stdout, redirected stderr, `TERM=dumb`, and unavailable alternate screen then yield different modes. Define the exact boolean predicate and failure fallback, including terminal initialization/restore errors.

- **The TUI event/update contract has no ownership for refreshes and actions.** A background refresh event can replace the selected entry while an action confirmation modal is open; one update implementation can execute against the stored `EntryId`, another against the current row index. Both follow Model/Event/Update/View and capability validation. Define selection by stable ID, modal target capture, generation checks, and behavior when the target disappears or changes before confirmation.

- **Keyboard and navigation behavior is wholly unconstrained.** Independent widget authors can choose different keys for quit, refresh, inspect, group expand/collapse, search, and actions; both use ratatui, themes, icons, and the Elm loop. This is observable product behavior and snapshot tests cannot reconcile implementations without a contract. Add a v1 interaction map, focus model, modal behavior, empty/loading/error states, and small-terminal degradation rules.

- **Theme and icon fallback selection is not deterministic.** One TUI can default to Unicode unless `--ascii` is passed; another can inspect locale or `TERM`; both offer ASCII and honor `NO_COLOR`. They can also select different colors for the same normalized state while all visual meaning retains text. Specify precedence among flags/environment/detection, the default icon set, the state-to-style token map, and behavior under monochrome/limited-color terminals.

- **Inspection output ownership permits incompatible behavior.** An `Inspector` can return structured domain sections for the presenter, while another can return capped text as a domain value; both exchange domain values and typed errors and avoid raw process objects. TUI and CLI inspection can then differ in logs, stderr merging, truncation, and provider-specific formatting. Define the inspection result schema, output caps, stderr policy, and compatibility mapping for the existing CLI.

- **`CommandRunner` behavior is not concrete enough for adapters to compose reliably.** One runner may treat nonzero exit as a successful `ProcessOutput` for adapters to interpret; another may return a typed execution error. Both use argv, deadlines, and output caps. Collectors can consequently classify the same missing tool, denial, or malformed response differently. Define spawn/not-found/timeout/nonzero/signal/UTF-8/truncation semantics and require a single process-result type.

- **The port boundary can still duplicate subprocess construction.** AD-3 says all host execution goes through `CommandRunner`, but each collector/inspector/action adapter may independently build argv, deadlines, and privilege prefixes. Two systemd units can obey the rule while choosing `sudo -n`, plain `sudo`, or no sudo, different flags, and different timeouts. Introduce provider command factories/policies or explicitly centralize provider-native argv construction and privilege policy within one adapter-owned component.

- **Fatal versus recoverable errors lack a composition-root exit contract.** The conventions distinguish diagnostics from fatal setup/output errors, but do not map errors to exit codes. Two CLIs can return `1` versus provider-specific codes, or produce a legacy table after partial failure versus abort output. Define exit-code classes and output rules for parse errors, collector failures, strict mode, broken pipe, TUI init failure, action refusal, and subprocess failure.

- **No shared fixtures are identified as the compatibility authority.** AD-11 requires captured fixtures and golden outputs, but two teams can capture different host outputs and both pass their own tests. Given this is a brownfield replacement, the existing Python executable and smoke contract need a fixed differential corpus. Name the authoritative fixtures/goldens, require Rust-versus-Python differential tests for each export and action mapping, and define intentional exceptions.

- **The “one binary crate” rule conflicts with enforceable architectural boundaries.** Rust module privacy can prevent some imports, but `pub(crate)` and sibling access allow presentation or adapters to reach concrete modules while still claiming inward dependencies conceptually. Two implementations can expose radically different internal APIs and both match the structural seed. Define visibility rules, allowed dependency edges, and a compile-time/lint strategy (or accept that AD-1 is a review convention rather than an enforceable invariant).
